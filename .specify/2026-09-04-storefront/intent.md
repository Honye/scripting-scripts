# Storefront — 多区 Apple 账号与订阅管家

- **状态**：Intent（意图澄清阶段，未进入设计/实现）
- **日期**：2026-09-04
- **平台**：Scripting (iOS)，TSX → SwiftUI
- **代号说明**：Storefront 取自 App Store 的 storefront（地区店面）概念，正式名待定

---

## 1. 背景与问题

养多个不同地区 Apple 账号的用户（为了买某区独占应用、蹭区域差价、拿 TestFlight 名额），长期面对一组没有工具承接的琐碎问题：

- 账号散落在备忘录/密码 App 里，**哪个号是哪个区、余额还剩多少**，全靠脑子记。
- 各区余额是**礼品卡充值的预付款**，不像信用卡会自动续费成功 —— 余额不足时订阅会**静默扣费失败**，用户往往在应用突然失效后才发现。
- 「这个 app 当年是用哪个号买的」是高频且痛苦的查询，重装/换机时尤其致命。
- TestFlight 名额是稀缺资源，链接收藏了一堆，不知道哪个已满、哪个还能进。

> **核心洞察**：这不是「订阅管理器」，市面上的订阅管理 App 都假设**单一支付账户**。本产品的独特价值在于 **account × region 这个二维度**，以及**预付余额**这个不同于信用卡的支付模型。

---

## 2. 目标用户

拥有 **2 个及以上不同地区 Apple 账号**的 iOS 重度用户。已在使用 Scripting，能接受「手动维护数据」的记账式心智。

**非目标用户**：只有一个账号的普通用户（他们用系统「订阅」页就够了）。

---

## 3. 目标 / 非目标

### 目标
1. 一处集中管理多区账号：地区、账号、密码（可选）、余额。
2. 订阅账单可预期：知道**下一笔什么时候扣、从哪个号扣、扣多少**，余额不够时提前预警。
3. 已购应用可追溯：随时查到某个应用是用哪个号买的、花了多少。
4. 降低录入摩擦：从 App Store 分享菜单一步入库。
5. TestFlight 资格集中管理，名额状态尽力跟踪。

### 非目标（明确不做）
- ❌ **不做自动化的地区/账号切换** —— iOS 无此能力（见 §5.2）。
- ❌ **不读取真实账单**：Apple 不开放任何第三方读取购买历史/余额/订阅状态的接口。**所有余额与订阅数据均由用户手动维护**，本产品是「记账本 + 提醒器」，不是「对账系统」。
- ❌ v1 不做跨设备同步（见 §4 决策）。
- ❌ 不做账号共享/多人协作。

## 4. 已确认的产品决策

| # | 议题 | 决策 | 理由 |
|---|---|---|---|
| D1 | 地区切换 | **只提供跳转 App Store 首页的入口 + 凭据一键复制**，切换动作由用户在系统内完成 | iOS 无程序化切换能力，不做超出能力的承诺 |
| D2 | 密码存储 | **Keychain 存储 + LocalAuth（Face ID）门禁**，查看/复制密码前必须生物识别 | Scripting 的 Keychain 是脚本级沙箱，安全边界清晰 |
| D3 | TF 名额监控 | **前台手动刷新为主 + widget 时间线刷新时尽力而为**，状态变化发通知 | 无真后台定时任务，UI 上须明示「不保证实时」 |
| D4 | 礼品卡购买 | **官方 + 三方链接本期一起做** | — |
| D5 | 三方链接来源 | **硬编码在脚本常量文件里**，随版本更新 | 无网络依赖、实现最简；改赞助商需发版 |
| D6 | 数据同步 | **v1 纯本地**，预留 JSON 导入/导出做备份与迁移 | 密码不出设备，安全边界最清晰 |
| D7 | 主界面组织 | **以账号为中心** | 契合「多区账号」的核心心智模型 |

## 5. 技术可行性结论（已实测）

### 5.1 确认可行

| 能力 | 实现路径 | 置信度 |
|---|---|---|
| 密码安全存储 | `Keychain`（**按脚本隔离**，别的脚本读不到，删脚本即销毁）+ `LocalAuth` 生物识别门禁 | 高 |
| 结构化数据存储 | `Storage`（JSON）足够；数据量增大可迁 `SQLite` | 高 |
| 订阅扣费提醒 | `Notification.schedule` + `CalendarNotificationTrigger`（`repeats: true`）。**扣费日是本地已知数据，无需联网即可准时提醒** | 高 |
| 分享菜单入库 | `intent.tsx` + `script.json` 的 `intentInputTypes: ["urls"]`，读 `Intent.urlsParameter`。App Store 分享出的 URL 形如 `https://apps.apple.com/cn/app/xxx/id123456789`，**可直接解析出 region + appId** | 高 |
| 应用元信息与售价 | `https://itunes.apple.com/lookup?id={id}&country={region}` —— 官方接口、免费、无鉴权，返回名称/图标/`formattedPrice`/`currency` | 高（已实测） |
| 应用详情页展示 | `AppStore.presentApp(id)` 可在 Scripting 内直接弹出 App Store 产品页 | 高 |

### 5.2 ❌ 确认不可行：自动切换地区/账号

两层都被系统堵死：

1. **改单账号地区**：Apple 要求余额清零 + 无进行中订阅才允许改区 —— 这恰恰是用户要养多个账号的原因。
2. **切换登录账号**：App Store 登录态由系统独占。第三方 App（含 Scripting）**既无法读取当前登录的是哪个账号，也无法触发登出/登录**。也不存在跳转到「账户 → 国家或地区」的 deep link，`itms-apps://` 只能打开 App Store 首页。

**因此 D1 的形态是「跳转 + 凭据复制 + 用户手动标记当前登录账号」。** UI 文案必须诚实，不能出现「一键切换」这种承诺。

### 5.3 ⚠️ 可行但走非官方路径：内购/订阅价格

**官方 iTunes Lookup API 完全没有内购字段**（已实测，返回中连 `hasInAppPurchases` 都没有）。

但 `https://apps.apple.com/{region}/app/id{id}` 的 HTML 中存在 `<script id="serialized-server-data">` 的 JSON blob，内含结构化的内购条目。以 Bear (id1016366447, us) 实测：

```
data[0].data.shelfMapping.information.items
  → { title: "In-App Purchases", summary: "Yes",
      items_V3: [
        { $kind: "textPair", leadingText: "Monthly Pro subscription", trailingText: "$2.99" },
        { $kind: "textPair", leadingText: "Yearly Pro subscription",  trailingText: "$29.99" }
      ]}
```

切换路径中的 `/us/` `/jp/` `/cn/` 即可取到对应区的币种与价格 —— **正好命中多区比价的核心场景**。

**风险与约束（必须写进实现约定）**：
- 非官方接口，Apple 改版随时可能失效 → **必须有降级路径：抓取失败时静默回落到用户手填**，绝不阻塞主流程。
- 字段标题会本地化（中文区为「App 内购买项目」）→ **按 `$kind === "textPair"` 的结构取值，不要按标题文案匹配**。
- Apple 只展示前 ~10 个内购项，非全量。
- 价格会变动 → 与用户已录入的价格做**差异提示**，而非静默覆盖（呼应用户「支持修改价格」的原始诉求）。
- 抓取需在 Scripting 中用 `fetch` 或 `WebScraper`；HTML 体积约 750KB，注意不要全量留驻内存。

### 5.4 ⚠️ 待验证：TestFlight 名额监控

**思路**：抓取 `https://testflight.apple.com/join/{code}` 页面，按内容判定「可加入 / 已满 / 已停止招募 / 链接失效」。

**当前状态**：用伪造 code 只得到 404，**未拿到真实页面样本，判定规则尚未验证**。→ 见 §7 开放问题 Q1。

**刷新时机是硬约束**：Scripting 没有真正的后台定时任务。唯一的后台执行窗口是 widget 时间线刷新（`Widget.present(view, reloadPolicy)`），而 iOS 按电量与使用习惯分配配额，**间隔不保证**（可能几十分钟，也可能数小时）。

> 结论：**做不到「名额一放出就抢到」**。产品定位应为「比你自己想起来查要早」，UI 上须明确这一预期，避免用户误以为是抢名额工具。

## 6. 功能范围（v1）

### 6.1 账号管理（核心）
- 字段：昵称 / 地区（storefront code + 国旗 + 币种）/ 账号 / 密码（可选，Keychain）/ 余额（手动）/ 备注
- 首页为账号卡片列表：地区旗、余额、本月待扣总额、**余额不足预警角标**
- 密码查看/复制前过 Face ID
- 「切换到此账号」：复制账号 → 提示 → 跳转 App Store → 返回后询问「是否已切换为当前账号」并更新标记
- 全局唯一的「当前登录账号」标记（手动维护）

### 6.2 订阅管理
- 字段：应用 / 关联账号 / 金额 + 币种 / 周期（月/季/年/自定义）/ 下次扣费日 / 是否启用
- 账号维度汇总：本月待扣、下次扣费日、**余额是否够付**
- 提前 N 天本地通知；余额不足时通知升级为 `timeSensitive`

### 6.3 已购 / 内购记录
- 字段：应用 / 购买账号 / 类型（买断 / 内购 / 订阅）/ 价格 + 币种 / 购买日期
- 新增时自动拉取应用名、图标、售价、内购价格（§5.3），全部**可编辑**
- 按账号、按应用两种浏览方式

### 6.4 TestFlight 记录
- 字段：应用 / TF 链接 / 关联账号 / 状态 / 最后检查时间
- 手动刷新 + widget 机会性刷新；状态变化发通知
- 明示「非实时」

### 6.5 礼品卡充值入口
- 按账号地区跳转 Apple 官方礼品卡页面
- 三方购卡渠道列表（硬编码常量，D5），**须带明确的第三方免责说明**

### 6.6 分享菜单录入
- `intent.tsx` 接收 App Store URL → 解析 region + appId → 拉取元信息 → 选择「记为已购 / 订阅 / TF」并关联账号

### 6.7 Widget
- 账号为中心：余额 + 近期扣费；余额不足高亮
- 承担 TF 状态的机会性后台刷新

## 8. 主要风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 用户期待「自动切区」而产品做不到，产生落差 | **高** | 文案与 onboarding 全程诚实表述；不使用「一键切换」字样 |
| 内购价格抓取因 Apple 改版失效 | 中 | 结构化取值 + 静默降级到手填；抓取失败不阻塞任何流程 |
| TF 刷新间隔不可控，用户误以为能抢名额 | 中 | UI 明示「非实时」，展示「最后检查时间」 |
| 全手动维护余额，数据很快失真，用户弃用 | **高** | 降低录入摩擦；订阅扣费日到期时主动推「余额还剩多少？」的一步更新 |
| 密码存储的信任门槛 | 中 | Face ID 门禁；明示 Keychain 脚本级隔离；密码字段完全可选 |

## 9. 成功标准（草案）

1. 用户能在 10 秒内答出「这个 app 是用哪个号买的」。
2. 订阅扣费前收到提醒，且**从未**因余额不足导致静默扣费失败。
3. 新增一条已购记录（从 App Store 分享进入）不超过 3 次点击。
4. 用户愿意持续维护余额数据 —— 这是产品存活的真正命脉。
